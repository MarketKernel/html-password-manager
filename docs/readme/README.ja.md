**Deterministic Password** は、パスワードを保存するだけでなく計算します。サイトのパスワードは、マスターパスワード、サイト、ユーザー名、バージョン番号から、Argon2id と HMAC-SHA-256 で導出されます。データベースファイルを失っても、同じ入力からはどのコンピューターでも同じパスワードが再び得られるので、ファイルの紛失はもう怖くありません。サイトのパスワードを変えるには、バージョンを上げます。仕組みは「[導出パスワード](#導出パスワード)」を参照してください。

また、完全な KeePass パスワードマネージャーでもあります。通常の `.kdbx` ファイル (KDBX 4、AES-256、Argon2id) を開き、編集し、保存するので、同じデータベースを KeePassXC、KeePass、KeeWeb でも引き続き使えます。導出したパスワードはほかのパスワードと同じようにエントリに保存され、ほかの KeePass アプリでも同じように表示されます。

すべてオフラインで動作します。アカウントもクラウドも不要で、ネットワークリクエストも一切ありません。アプリ全体が単体の HTML ファイル 1 つに収まっています。データベースはページのメモリ内で復号されてそのままディスクに保存され、マスターパスワードがページの外に出ることはありません。同じページは、隣のタブにログイン情報を入力する [Chrome 拡張機能](#chrome-拡張機能)としても動作します。**[Chrome ウェブストアからインストールできます](https://chromewebstore.google.com/detail/hiahfdknjchamepclnokcalkcjcfhahf)**。

**[オンライン版](https://password.marketkernel.com/)** は、同じページを PWA (Progressive Web App) にしたものです。システムにインストールすると、専用のウィンドウとアイコンを持つ独立したアプリとして動作し、オフラインでも使えます。パソコンの Chrome、Edge、Arc ではアドレスバーのインストールボタンを、Android では Chrome の ⋮ メニュー →「アプリをインストール」を、iOS では Safari または Chrome で 共有 →「ホーム画面に追加」を使います。この場合もデータベースはディスク上に置かれたままです。「[GitHub Pages](#github-pages)」を参照してください。

## 使い方

1. `build/password-manager.html` をビルドし (「[ビルド](#ビルド)」を参照)、ブラウザで開きます。ディスクから直接開いてかまいません。
2. 「ファイルを開く」→ `.kdbx` データベースを選択するか、ウィンドウにドラッグします。
3. マスターパスワードを入力し (データベースにキーファイルがある場合はそれも選択し)、「ロック解除」を押します。

Chrome、Edge、Arc では、ファイルは File System Access API を通じて開かれます。変更は同じファイルに書き戻され (自動保存がオンなら、編集のたびに少し遅れて)、次回アクセスしたときにはそのファイルが再び提示されます。記憶されるのはファイルのハンドルだけで、内容やパスワードが記憶されることはありません。Safari と Firefox ではファイルは読み取り専用で開かれ、「保存」を押すと更新されたデータベースのコピーがダウンロードされます。スマートフォンでも同様です。Android の Chrome には File System Access がなく、iOS のブラウザは Chrome も含めてすべて Safari のエンジンで動いているためです。iOS では、「保存」を押すとコピーがダウンロードされる代わりに共有シートに渡されます。「[スマートフォンでの利用](#スマートフォンでの利用)」を参照してください。

「新規データベース」は、AES-256 と Argon2id (64 MiB、10 パス。KeePassXC の既定値で、ブラウザでは約 0.5 秒) で暗号化された空の KDBX 4 データベースを作成します。

### スマートフォンでの利用

幅 900 ピクセルまで (スマートフォン、または縦向きに持ったタブレット) では、ページは一度に 1 つのものだけを表示します。エントリリストが画面全体に広がり、タップするとエントリが専用の画面で開きます。ツールバーの ‹、システムの戻るボタン、または戻るスワイプでリストに戻ります。戻るときに編集内容は保持されます。パソコンで別のエントリを選んだときに保持されるのと同じです。空のまま残された新規エントリは破棄されます。☰ を押すと、グループ、タグ、ごみ箱がリストの上にスライドして現れます。メニュー、パスワード生成、設定は画面の下からせり上がって表示されます。戻る操作はまずそれらを閉じ、ダイアログならキャンセルします。パスワード生成、設定、ロックはツールバーの ⋯ メニューにあります。

タッチスクリーンには右クリックもドラッグもありません。グループの横の ⋯ を押すと、パソコンで右クリックしたときに開くメニューが開き、その中の「グループへ移動…」がドラッグの代わりになります。エントリのメニューは、エントリの画面にある ⋯ です。

ファイルは読み取り専用で開かれます。iOS では、「保存」を押すと更新されたデータベースが共有シートに渡され、「“ファイル”に保存」で元のファイルと置き換えられます。シートを閉じると、変更は保存されないままになります。Android の Chrome が共有できるのは画像、音声、動画、テキストだけなので、そこでは「保存」を押すとコピーがダウンロードされます。

それより幅が広い画面とタブレットでは、パソコンと同じく 3 つのペインがそのまま表示されます。タッチスクリーンでは、サイズにかかわらずボタンが大きくなり、グループの横に ⋯ が表示されます。

## Chrome 拡張機能

**[Chrome ウェブストアからインストール](https://chromewebstore.google.com/detail/hiahfdknjchamepclnokcalkcjcfhahf)**

`npm run build` は `build/extension/` も出力します。これは同じアプリを Chrome 拡張機能にしたもので、Chrome ウェブストア向けにそれをまとめた `build/password-manager-extension-<version>.zip` も作られます。自分でビルドしたものを試すには、`chrome://extensions` → デベロッパー モード →「パッケージ化されていない拡張機能を読み込む」→ `build/extension` を選びます。

ツールバーのアイコンを押すと、コンパクトなポップアップが開きます。タブのサイトのエントリが表示され、クリックするとそのエントリが入力されます。ユーザー名、パスワード、ワンタイムコードをコピーするボタンと、データベース全体の検索もあります。下部の **フルモード** を押すと、アプリが Chrome のサイドパネルでページの横に開き (パネルは幅が狭いので、スマートフォン向けのレイアウトになります)、タブを切り替えても開いたままになります。そこではファイル版と同じようにすべての機能が使えます。拡張機能が加えるのは、ログイン情報の入力です。

- **ポップアップ** は、パネルが最後に開いたファイルを、マスターパスワードだけでロック解除します。ファイルやキーファイルの選択と、すべての変更はパネルで行います。エントリのないサイトでは、ポップアップの **新しいパスワード** を押すと、メニューの「入力」と同じように、パスワード生成を表示した状態でパネルが開きます。
- ページのコンテキストメニュー (ページ上またはフィールド内で右クリック) の **入力** は、タブのサイトのエントリのユーザー名とパスワードを入力します。サインインの途中でワンタイムコードを求められる段階では、そのエントリのワンタイムコードを入力します。そのサイトのエントリが 1 つだけなら、パネルが開いているかどうかに関係なく、すぐに入力されます。複数ある場合、1 つもない場合、データベースがロックされている場合はパネルが開き、エントリを選ぶ、パスワードを作る、ロックを解除する、のいずれかを行うと、そこから入力が続きます。2 段階のサインイン (Google、Microsoft) では、1 段階目でユーザー名、2 段階目でパスワードを入力します。タブ用に選んだエントリは記憶されます。パネル内のエントリにある **入力** ボタンは、そのエントリをタブに入力します。
- **データベースは開いたままです。** パネルを閉じても、ロックされるまでは開いています。ロックされるのは、設定の無操作時間が過ぎたとき、パソコンの画面がロックされたとき、パネルやポップアップからロックしたとき、ツールバーアイコンのメニューの **ロック** を押したときです。もう一度開くと、パネルはパスワードなしで続きから使え、ポップアップもすぐにデータベースを表示します。
- グループパネルの一番上にある **このサイト用** には、タブのサイトのエントリが一覧表示され、リストは最初にこれを表示します。タブの切り替えに追従します。
- **ページ用の新しいパスワード。** エントリのないサイトでは、「入力」を押すと、タブのサイトとページに入力されたユーザー名を使って 導出 v3 のパスワード生成が開きます。そこの「入力」ボタンを押すとパスワードが入力され (登録フォームなら両方のフィールドに)、通常のエントリとして保存されます。

エントリがタブに合致するのは、エントリの Web サイトがタブのサイトを正確に示している場合です。どちらのアドレスも generator 3 の `siteOf()` で処理されます。スキーム、ポート、パス、`www.` は取り除かれ、IDN は punycode になります。`google.com` は `accounts.google.com` に合致せず、`mail.site.com` も `site.com` に合致しません。`https://` 付き、またはスキームなしのエントリが `http://` のページに入力されることはありません。http で使うサイトでは、Web サイトに `http://` を含める必要があります。ごみ箱のエントリは候補に出ません。また、別のサイト用のエントリを手動で選んだ場合は、両方のサイトを示す警告を表示したうえでのみ入力されます。

**仕組み。** パネルはページそのものです。Manifest V3 の要件どおり、`panel.html` とそのスクリプトの `panel.js` からなります。ロック解除と保存のたびに、パネルはファイルとそのキー (`ProtectedValue` に入ったパスワードとキーファイル) をオフスクリーンドキュメントに渡します。オフスクリーンドキュメントはそれらと、それらで復号したデータベースの読み取り専用コピーを、ロックされるまでメモリ上に保持します。ロックするとオフスクリーンドキュメントは閉じられ、キーも一緒に消えます。どこにも何も書き込まれません。メニューはサービスワーカーが受け持ちます。「入力」のクリックでパネルを開けるのは何かを await する前だけなので、ワーカーは入力できるかどうかをすぐに判断しなければなりません。そのためワーカーは、オフスクリーンドキュメントから送られてくるエントリの Web サイト (名前もパスワードも含みません) を保持しており、オフスクリーンドキュメントがワーカーを動かし続けます。ポップアップ (`popup.html`、`popup.js`) は何も復号しません。タブに合致するタイトルとユーザー名をオフスクリーンドキュメントに問い合わせ、次にクリックされた 1 つのエントリを問い合わせます。ロックされている場合は、最近使ったファイルを読み込み、パスワードと一緒にそのドキュメントに渡して開かせます。

**ページに渡るもの。**

- クリックで求められたものだけで、しかも 1 つのエントリの値だけです。コンテンツスクリプトはどこでも動作しません。クリック時に、`chrome.scripting.executeScript` がまずタブのすべてのフレームに、どこにあるか、どんなログインフィールドがあるかを問い合わせます。このとき値は送りません。そのあとエントリのサイトのフレームだけが値を受け取り、関数は入力する前に自分のアドレスをもう一度確認します。同じページ内にある別のサイトのフレームには何も渡りません。
- 入力されるのは、人に見えるフィールドだけです。表示されていて、有効で、書き込み可能で、ある程度の大きさがあり、ウィンドウ内にあるものです。罠として隠されたフィールドは空のままです。
- 値は拡張機能の isolated world から設定されるので、ページが入力欄に仕掛けた setter は通りません。`input` と `change` イベントで React、Vue、Angular に変更を知らせます。
- マスターパスワード、ほかのエントリ、サイトの一覧がページに渡ることはありません。

**権限。** すべてのサイトではなく `activeTab` を使います。アイコンか「入力」をクリックすると、拡張機能にその 1 つのタブが与えられます。そのため、パネルはポップアップかメニューから開き、Chrome 自体の設定 (`openPanelOnActionClick`) で開くことはありません。その方法で開いたパネルには、タブがまったく与えられないからです。与えられていないタブでパネルの「入力」を使うと、エントリのサイトへのアクセス許可が一度だけ求められます (`optional_host_permissions`)。`contextMenus`、`scripting`、`sidePanel` は上記のため、`offscreen` はドキュメントのため、`idle` は画面ロックのため、`clipboardWrite` はパネルを閉じた状態でもコピーした秘密情報を消去するためです。`externally_connectable` はありません。拡張機能の各部分は `chrome.runtime` を通じてやり取りし、それぞれ拡張機能自身のページからのメッセージしか受け付けません。拡張機能のページには、ファイル版と同じく `connect-src 'none'` が設定されています。ビルドは、これが設定されていること、そしてインラインスクリプトや外部アドレスを含むページがないことをチェックします。

ファイル版との違いが 1 つあります。もう一度開いたとき、パネルがデータベースをその場で書き込めるのは、Chrome がまだそれを許可している場合だけです。許可されていなければステータスバーにそう表示され、最初の「保存」で許可が求められます。

## セキュリティ

- **ページの外には何も出ません。** ファイル内の Content-Security-Policy が、すべてのネットワークリクエスト、フォーム送信、外部リソースを禁止しています。ポリシーが失われたり外部参照が入り込んだりすると、ビルドは失敗します。PWA 版では、マニフェスト、サービスワーカー、アイコンの 3 つを追加で許可していますが、いずれも自身のオリジンからのもので、`connect-src` は `'none'` のままです。
- 形式を扱うコードは、KeeWeb の基盤となっているライブラリ [kdbxweb](https://github.com/keeweb/kdbxweb) です。Argon2 は [hash-wasm](https://github.com/Daninet/hash-wasm) の WebAssembly で、これもファイルに埋め込まれています。
- 保護されたフィールドは、メモリ上では XOR マスクされた状態で保持され (kdbxweb の `ProtectedValue`)、画面上でも表示操作をするまで伏せられています。検索が保護されたフィールドの中を調べることはありません。
- **どの言語のパスワードでも。** ブラウザがあるフィールドをパスワード欄とみなすと、macOS は Secure Input をオンにしてラテン文字のキーボードレイアウトを強制するため、キリル文字のマスターパスワードを入力できなくなります。Chrome がパスワード欄とみなすのは `type=password` だけではありません。ヒューリスティックによって、`-webkit-text-security` でスタイル指定されたフィールドや、点の並んだ値を持つフィールドもパスワード欄とみなし、一度そうみなすとその扱いを続けます。このアプリの秘密情報のフィールドは、そうした手がかりを与えません。普通のテキスト入力欄で文字を透明にし、その上に点のレイヤーを描いています (キャレットの位置がずれないよう、等幅フォントで)。隠されたテキストがキリル文字 (РУС) とラテン文字 (ENG) のどちらで入力されているかは、バッジで示されます。その代償として、ほかのアプリからキー入力を隠す役割もある Secure Input は一切使われません。
- コピーした秘密情報は、30 秒後とロック時にクリップボードから消去されます。
- データベースは、15 分間操作がないとき、および `⌘L` でロックされます。ロックすると、復号されたデータベースはメモリから破棄されます。書き込めない未保存の変更があるときは、ロックは変更を捨てずに待機します。
- エントリ内のリンクは `http`、`https`、`ftp`、`mailto` の場合にのみ、`noopener` 付きで開きます。
- パスワードは `crypto.getRandomValues` と棄却サンプリングで生成されます。どの文字も等しい確率で出現します。

## 機能

- **グループ**: 折りたたみ可能なツリー。コンテキストメニューでの作成、名前の変更、削除。ドラッグ&ドロップでの移動 (エントリとグループ)。サイズ変更と非表示ができるパネル (`⌘\`)。
- **エントリ**: タイトル、ユーザー名、パスワード、Web サイト、メモ、カスタムフィールド (プレーンテキストまたは保護あり)、タグ、有効期限、添付ファイル。タイトル、ユーザー名、Web サイト、日付での並べ替え。
- **ワンタイムコード** (TOTP): `otp` フィールド (KeePassXC や KeeWeb が保存する形式の `otpauth://` URL、またはシークレットそのもの)、KeePass の `TimeOtp-*` フィールド、TrayTOTP の `TOTP Seed` から生成します。SHA-1、SHA-256、SHA-512 に対応し、コードはカウントダウン付きで更新されます。エディタの **+ ワンタイムコード** は、サイトが QR コードの横に表示するセットアップキー (または `otpauth://` リンク) を受け取り、すぐにコードを表示するので、サイト上で確認できます。キーだけの場合は、KeePassXC が読める形式の `otpauth://` リンクとして保存されます。
- **編集** は下書き上で行われます。「保存」を押すと、KeePass と同じように、まず以前の状態がエントリの履歴に保存されます。「キャンセル」を押すと下書きは破棄されます。以前のバージョンを閲覧して復元することもできます。
- **ごみ箱**: 削除するとごみ箱に移動し、そこから復元するか、完全に削除できます。
- **検索**: タイトル、ユーザー名、Web サイト、メモ、タグ、カスタムフィールド、添付ファイル名を対象にします。クエリのすべての単語が一致する必要があります。
- **パスワード生成** (サイコロ、`⌘G`) は、リストで選んだ種類のパスワードを作成します。リストは新しい導出方式から順に並び、最後の選択は記憶されます。
  - **導出 v3**: マスターパスワード、ユーザー名、サイト、バージョンから計算されるので、ファイルがなくても再計算できます。「[導出パスワード](#導出パスワード)」を参照してください。
  - **導出 v2** と **導出 v1**: 2 つの旧プログラム (legacy 2 と legacy 1) の計算方式です。設定 →「旧式のパスワードアルゴリズムを表示」がオンのときにリストに表示されます。「[旧式のアルゴリズム](#旧式のアルゴリズム)」を参照してください。
  - **ランダム**: 長さ、文字種、紛らわしい文字、エントロピーの推定値。

  入力したパスワードの強度メーター。
- **データベース**: 名前の変更、マスターパスワードとキーファイルの変更、コピーの保存。
- **言語**: English、中文、हिन्दी、Español、Français、العربية、বাংলা、Português、Русский、اردو、Bahasa Indonesia、Deutsch、日本語、मराठी、తెలుగు、Türkçe (話者数の多い上位 16 言語) とУкраїнська。設定で選ぶか、ブラウザの言語が使われます。アラビア語とウルドゥー語では、ウィンドウが右から左のレイアウトになります。
- **テーマ**: 設定で、システムに合わせる、ライト、ダークから選べます。言語、テーマ、パネルの幅、並べ替え、パスワード生成のオプション、折りたたんだグループは記憶されます。

## 導出パスワード

パスワード生成の **導出 v3** は、次のものからパスワードを計算します。

- データベースのマスターパスワード (キーファイルがあっても使いません)、またはそこで入力した別のマスターパスワード
- ユーザー名
- サイト: アカウントがあるドメイン (`https://www.github.com/login` → `github.com`)
- バージョン: 1、2、… 2³² − 1 まで。「+1」で同じアカウントに新しいパスワードが作られます。

この 4 つから 32 バイトのエントロピーが作られます。条件 (長さ、文字種、紛らわしい文字) は、そのバイト列を文字に整形するだけなので、変えてもエントロピーは変わりません。**使用** を押すと、結果が通常の保存されたパスワードとしてエントリに入ります。どう作られたかの情報は何も残りません。エントリはほかのエントリと何も変わらず、ほかの KeePass アプリでも同じパスワードが表示されます。ファイルを失っても、同じマスターパスワード、ユーザー名、サイト、バージョン、条件があれば、どのマシンでも同じパスワードが得られます。既定値は 20 文字、4 つの文字種すべて、紛らわしい文字なしです。ほかの条件で作ったパスワードは、その条件も覚えておく必要があります。

パスワード生成は、まずユーザー名を尋ねます。エントリから開いた場合はそのエントリ自身のユーザー名で、そこに入力した内容はフォームにも反映されます。次にサイトを尋ねます。どちらも必須で、それらから得られるパスワードは一番下の **使用** の上に表示されます。

- メールアドレスのユーザー名は、それ自体がサイトを示しています。`test@site.com` なら `site.com` が入力され、エントリの Web サイトはそのまま残ります (`mail.site.com` かもしれないからです)。ただし、同じアドレスで多くのサイトにサインインするものなので、パスワード生成はフィールドの下にその旨を表示します。`test@gmail.com` で GitHub を使う場合は、自動で入った `gmail.com` を `github.com` に書き換えてください。
- それ以外のユーザー名ではサイトを入力する必要があり、エントリから開いた場合は、入力した内容がエントリの Web サイトにもなります。最初は、エントリにすでにある Web サイトが入力されています。

サイトとして入力したもののうち、スキーム、パス、ポート、先頭の `www.` は関係ありませんが、サブドメインは区別されます。`login.github.com` と `github.com` は別のサイトです。URL でないサイト (「私の銀行」) はそのまま使われます。ツールバーから開いたパスワード生成も、専用のフィールドを使って同じように動作し、結果をコピーします。

「データベースのマスターパスワードを使用」は、パスワード生成を開くたびにチェックが入った状態になります。チェックを外すと、別のマスターパスワードから導出できます。そのパスワードはそこで入力し、どこにも保存されません。別のデータベースで作ったパスワードや、マスターパスワードを変更する前に作ったパスワードを復元するときに使います。マスターパスワードを変更しても、ファイル内のパスワードはそのまま残ります。変わるのは、それ以降にパスワード生成が計算する結果だけです。

### アルゴリズム: generator 3

以下はすべて固定されています。定数を 1 つでも変えると、それで作ったすべてのパスワードが再計算できなくなります。将来の生成方式はリストに新しい種類として追加され、この方式はそのまま残ります。コードは `src/core/derived.ts` です。`npm test` は、固定のベクトルと、この説明をもとに Node 標準の `crypto` で書かれた独立した実装の両方と照合してチェックします。プリミティブは標準的なもの (SHA-256、HMAC-SHA-256、Argon2id) なので、アルゴリズムはどの言語でも再実装できます。

処理は 2 段階です。秘密情報が 32 バイトのエントロピーになり、次に条件に従ってそのバイト列から文字が切り出されます。

**ステージ 1: エントロピー。**

1. *入力を正規化します。* 文字列はすべて UTF-8 です。
   - `site`: サイトとして入力されたもののホストです。テキストを WHATWG URL としてパースし (テキストに `scheme://` がなければ先頭に `https://` を付けます)、小文字にし、IDN は punycode に、ポートは除き、ユーザー名やパスワードも除き、先頭の `www.` を削除します。URL としてパースできないテキストはそのまま使います。そのあと前後の空白を除き、NFC 正規化し、小文字にします。
   - `user`: ユーザー名です。前後の空白を除き、NFC 正規化します。大文字と小文字はそのまま保たれます。
   - `master`: マスターパスワードです。NFC 正規化し、空白は一切除きません。「é」を 1 文字で入力しても、「e」と結合アクセントで入力しても、同じパスワードになります。
2. *ソルト。*
   ```
   salt = SHA-256( "html-password-manager/derived/v3" ‖ 0x00
                   ‖ u32be(byte length of site) ‖ site
                   ‖ u32be(byte length of user) ‖ user
                   ‖ u32be(version) )
   ```
   長さのプレフィックスによって `ab` + `c` と `a` + `bc` が区別されます。ラベルによって、これらのバイト列が同じ入力のほかの用途と区別されます。`u32be` は 4 バイトのビッグエンディアン整数です。
3. *ストレッチ。*
   ```
   entropy = Argon2id(password = master, salt, memory = 64 MiB, passes = 3,
                      lanes = 1, version 0x13, output = 32 bytes)
   ```
   Argon2id によって、マスターパスワードを 1 回推測するごとに 64 MiB のメモリが必要になります。これが GPU や ASIC による攻撃を遅くします。サイト、ユーザー名、バージョンがソルトに含まれているので、アカウントごとにソルトが異なります。事前にテーブルを計算しておくことはできず、アカウントは 1 つずつ個別に攻撃するしかありません。

**ステージ 2: 整形。** 条件はここでしか使われないので、変わるのはパスワードの見た目であり、その背後にあるエントロピーではありません。

4. *ランダムなバイトのストリーム* を必要なだけ作ります。長いパスワードとそのシャッフルには 32 バイトでは足りません。
   ```
   block(i) = HMAC-SHA-256(key = entropy, "hpm-v3-stream" ‖ u32be(i)),  i = 0, 1, 2, …
   ```
5. *n 未満の偏りのない数。* ストリームの次の 4 バイトをビッグエンディアンの u32 `x` として取り出します。`x ≥ 2³² − (2³² mod n)` なら捨てて次を取り出し、そうでなければ結果は `x mod n` です。(単純な `x mod n` では、アルファベットの先頭の文字が出やすくなります。)
6. *文字。* 文字種は次の順で、選ばれたものだけを使います。
   ```
   A–Z      ABCDEFGHIJKLMNOPQRSTUVWXYZ
   a–z      abcdefghijklmnopqrstuvwxyz
   0–9      0123456789
   symbols  !#$%&*+-=?@^_~.,:;()[]{}<>/|
   ```
   紛らわしい文字なしの場合は、そこから `O 0 o I l 1 |` が取り除かれます。続いて次のようにします。
   ```
   chars = []
   for each chosen set:            chars.push(set[draw(|set|)])      # どの文字種も必ず含まれる
   while |chars| < length:         chars.push(all[draw(|all|)])      # all = 文字種をすべてつなげたもの
   for i = length − 1 down to 1:   j = draw(i + 1); swap chars[i], chars[j]   # Fisher–Yates
   password = chars joined
   ```
   長さは 4〜128 です。最初に各文字種から 1 文字ずつ取ることで、「数字を含む」「記号を含む」が保証されます。シャッフルによって、それらの文字がどこに入ったかはわからなくなります。

**テストベクトル。** マスターパスワード `Тестовый пароль`、サイト `https://www.github.com/login` (`github.com`)、ユーザー名 `me@example.com`、バージョン 1、既定の条件 (20 文字、4 つの文字種すべて、紛らわしい文字なし):

```
password  A6qVXXF]7<%a)aa<x7*U
```

同じエントロピーで 12 文字、記号なしにすると `yaM6VJaJFYUQ` に、既定の条件でバージョン 2 にすると `3q_bwppbE8P2+ufKr:P6` になります。

### 強度について

- 導出パスワードのエントロピーは最大 256 ビット (32 バイト) です。4 つの文字種すべてを使い、紛らわしい文字を除いた 20 文字は約 128 ビットです。実際には、上限を決めるのはマスターパスワードです。
- **導出パスワード方式に共通する弱点:** あるサイトからパスワードが漏洩すると、サイトとユーザー名はわかっているので、攻撃者はオフラインでマスターパスワードを推測できます。1 回の推測には、64 MiB を使う Argon2id の実行 1 回分のコストがかかります。ブラウザでは約 0.15〜0.4 秒で、専用ハードウェアではそれより短くなります。短いマスターパスワードやありふれたマスターパスワードは見破られますが、長いパスフレーズなら見破られません。ランダムなパスワードにはこの弱点がありません。パスワード生成に両方があるのはそのためです。
- マスターパスワードが破られない限り、漏洩したパスワードからほかのサイトやバージョンについては何もわかりません。それらは別のソルト、つまり別の Argon2 の実行から得られるからです。

データベースが開いている間、マスターパスワードは、それまでに計算したエントロピーとともに、メモリ上で XOR マスクされて保持されます。ロックするとどちらも破棄されます。

## 旧式のアルゴリズム

2 つの古い Windows プログラムが、秘密フレーズからパスワードを計算していました。パスワード生成の **導出 v1** (legacy 1) と **導出 v2** (legacy 2) はそれらを正確に再現するので、それらで作ったパスワードを復元できます。これらは計算機です。入力したものは何も保存されず、フレーズはパスワード生成を閉じると消え、**使用** を押すと結果が通常の保存されたパスワードとしてエントリに入ります。設定 →「旧式のパスワードアルゴリズムを表示」で表示されるようになります。

エントリから開くと、どちらも識別子を提案します。すでにサイトを示しているユーザー名 (`mail@site.com`) はそのまま、それ以外はユーザー名、`@`、`www.` を除いたサイトをつなげたもの (`dmytro@github.com`) です。識別子は変更できます。各フレーズ (マスターキーとセカンダリキー、プライマリ秘密フレーズとセカンダリ秘密フレーズ) には、それぞれ「データベースがロックされるまで記憶」のチェックボックスがあります。チェックを入れたものはページのメモリ上に XOR マスクされて保持され、次回自動で入力されます。最初のフレーズが保持されていれば、キーはすぐに計算されます。どちらも、データベース自身のマスターパスワード (ロック解除に使ったもの) を最初のフレーズ、つまり legacy 1 のマスターキーまたは legacy 2 のプライマリ秘密フレーズとして使うこともできます (「データベースのマスターパスワードを使用」。それぞれについて設定に記憶されます)。その場合、そのフィールドとチェックボックスは無効になります。これらがディスクに書き込まれることはありません。ロックする、データベースを閉じる、または旧式のアルゴリズムをオフにすると、すべて消去されます。コードは `src/core/legacy.ts` です。`npm test` は、元の .NET プログラムで計算したベクトルと照合してチェックします。

**Legacy 1**: マスターキー、識別子、プライマリキー、セカンダリキー、結果。

```
short(bytes) = Base64(bytes) without "=", "/", "+", first 10 characters
primary key  = short(SHA-1 applied 1 000 000 times to UTF-8(master key ‖ identifier))
result       = short(SHA-1(UTF-8(primary key ‖ secondary key)))
```

プライマリキーは識別子に結び付いていて、別に (紙などで) 保管しておけるので、マスターキーをどこにも入力する必要はありません。プライマリキーを直接入力できます。セカンダリキーがあるので、盗まれたメモだけでは役に立ちません。

**Legacy 2** (Password.Generator 1.0): プライマリ保護は識別子、プライマリ秘密フレーズ、キーの長さ、文字種。セカンダリ保護はキー、セカンダリ秘密フレーズ、パスワードのバージョン、パスワードの長さ、文字種です。

```
digest(a, b, v, n) = SHA-1 applied n times to UTF-8(a) ‖ UTF-8(b) ‖ (v > 0 ? u32le(v) : nothing)
key                = select(digest(identifier, primary phrase, 1, 100 000), key length + 2)
password           = select(digest(key, secondary phrase, version, 1), password length + 2)
```

`select` は、ダイジェストを 5 つのリトルエンディアン u32 として読み、それぞれの最上位ビットを立て、アルファベットの N 進数で最下位の桁から書き出し、それぞれ 5 文字ずつ取って、長さ (1〜18) に切り詰めます。アルファベットは `!#$%&'()+,-.` (選んだ場合)、数字 (常に)、A–Z と a–z (選んだ場合) です。先頭の 2 文字は、プログラムが表示したものと目で照合するための署名で、残りがキーまたはパスワードです。キーのバージョンは常に 1 です。プログラムにそのためのフィールドがないからです。識別子 `1`、フレーズ `1`、長さ 10、数字と英字を選ぶと、キーは `E8 8pgYm9fZha` になります。

どちらもバージョン 3 よりはるかに弱い方式です。フレーズを 1 回推測するのに攻撃者が払うコストは、64 MiB を使う Argon2id の実行 1 回ではなく、SHA-1 の実行数回分にすぎません。また、Legacy 1 の結果は 10 文字で、約 60 ビットです。古いパスワードの復元に使い、新しいパスワードには使わないでください。

## 翻訳

英語のテキストはコード内にそのまま置かれます。`t('menu', 'Delete')`、`tn('status', '{count} entry', '{count} entries', n)`、テンプレート内の `data-i18n="context"` / `data-i18n-attr="context"` です。最初の引数はコンテキストで、その文字列が属するインターフェースの部分を表します。これにより、同じ英単語を 2 つの場所で別々に翻訳できます。辞書 `src/locales/<code>.json` は、コンテキスト → 英語のテキスト → 翻訳 を対応付けます。

```json
{
  "menu": { "Delete": "Удалить" },
  "status": { "{count} entries": { "one": "{count} запись", "few": "{count} записи", "many": "{count} записей", "other": "{count} записи" } }
}
```

辞書にない文字列は英語で表示されます。数を含むテキストは、その言語の複数形カテゴリ (`Intl.PluralRules`) ごとに 1 つの形を持ち、英語の複数形をキーにします。`npm run i18n` は、言語ごとに、まだ翻訳されていない文字列と、もう使われていない文字列を一覧表示します。`npm test` は、すべての翻訳が英語のプレースホルダーを保ち、すべての複数形を備えているかをチェックします。

Chrome が拡張機能そのものについて表示するもの (名前と説明、ツールバーボタンのタイトル) は、パネルの言語ではなく、`chrome.i18n` を通じてブラウザの言語に従います。これらのテキストは `src/extension/manifest.json` にある英語のもので、同じ辞書のコンテキスト `manifest` の下で翻訳されます。ビルドはそれらを `_locales/<code>/messages.json` に書き出し、マニフェストに `__MSG_appName__` などを入れます。Chrome には独自の言語コードがあり、それ以外は無視されます。`pt` は `pt_BR` と `pt_PT` に、`zh` は `zh_CN` になります。ウルドゥー語にはコードがないため、そこでは Chrome は拡張機能の名前を英語で表示します。名前が 75 文字、説明が 132 文字を超えると、ビルドは停止します。

この README も翻訳されています。`docs/readme/README.<code>.md` が言語ごとに 1 つあり、それぞれの先頭に言語の一覧があります。ここを変更したら、翻訳にも反映してください。

## ビルド

```sh
./build.sh         # 必要なら依存関係をインストールしてから build/password-manager.html をビルド
npm install
npm run build      # -> build/password-manager.html
npm run watch      # src/ が変更されたら再ビルド
npm run typecheck  # tsc --noEmit
npm test           # .kdbx ファイルの読み込み・編集・保存、パスワード生成、TOTP、導出パスワード、タブとの照合、辞書
npm run test:browser  # ビルドしたページと拡張機能をヘッドレス Chrome で
npm run i18n       # 各辞書に足りない文字列、不要になった文字列
npm run check      # typecheck、test、build、test:browser を順に
npm run shots -- shots/after  # ビルドしてから主な画面のスクリーンショットを shots/after に
```

`build.mjs` は esbuild で `src/app/main.ts` を IIFE にバンドルし、スタイルとアイコン (data URI) とともに `src/app/template.html` に埋め込みます。kdbxweb の Node 向けフォールバック (`crypto`、`@xmldom/xmldom`) は空のスタブに置き換えられます。ブラウザには `crypto.subtle` と `DOMParser` があるからです。出力は `build/password-manager.html` で、約 500 KB、そのうち 4 分の 1 が辞書です。

同じ実行で `build/pages/` も書き出されます。これはそのページをインストール可能な PWA にしたもので、マニフェストへのリンクと、ページに自身のワーカーを登録させる `<meta name="service-worker">` を含む `index.html`、`manifest.webmanifest`、アイコン、そしてページをキャッシュしてオフラインで開けるようにする `sw.js` からなります。`build/password-manager.html` 自体は、外部参照のない単一ファイルのままです。

さらに `build/extension/` も書き出されます。`panel.html` は、スクリプトを `panel.js` に分けたテンプレートです。中身は同じ `src/app/main.ts` ですが、`src/app/platform.ts` の代わりに `src/extension/extension.ts` が使われます (`src/app/platform.ts` のフックはファイル版では何もしません)。その横に `popup.html` (ページのスタイルと `popup.css` を含みます) と `popup.js`、`background.js`、`offscreen.html` と `offscreen.js`、アイコン、そして `package.json` のバージョンを持つ `manifest.json` が並びます。`build/password-manager-extension-<version>.zip` には同じファイルが日付を固定して収められているので、同じソースからは同じバイト列が得られます。

`tests/extension.mjs` は、DevTools プロトコル (パイプ経由の `Extensions.loadUnpacked`。`--load-extension` は Chrome 137 以降なくなりました) を通じてその拡張機能をヘッドレス Chrome に読み込み、ローカルサーバー上のテストサイトに入力します。対象は、普通のフォーム、React 風のフォーム、ワンタイムコードを含む 3 段階のサインイン、そのサイト自身のフレームと別のサイトのフレーム、罠として隠されたフィールド、https のエントリに対する http のページ、導出 v3 のパスワードで入力する登録フォームで、パネルを閉じた状態とロック後の両方で試します。さらに、ロック解除、入力、検索、コピー、ロックを行うポップアップもテストします。コンテキストメニューは DevTools からクリックできないので、テストはワーカーの `onClicked` を直接発火させます。実際のクリックがないと Chrome は `activeTab` を与えないため、テスト対象のコピーは、ホスト権限としてテストサイト (`*.test`) にアクセスできるようになっています。ツールバーのアイコンは DevTools からクリックできます (`Extensions.triggerAction`)。ビルドしたままの拡張機能を入れた専用の Chrome で、そのクリックによってポップアップにタブが与えられることを確認します。ヘッドレス Chrome 153 は、拡張機能に関係なくそのクリックでクラッシュするため、その場合このチェックはスキップされます。Chrome for Testing ではこのチェックが実行されます (`CHROME=/path/to/chrome-for-testing npm run test:browser`)。

`tests/fixtures/Database.kdbx` はテスト用のサンプルデータベースで、パスワードは `Тестовый пароль` です。

## バージョンとリリース

バージョンは `package.json` の 1 か所にだけ書かれています。ビルドはそれを、ページ (開始画面の下の行、設定画面の一番下)、拡張機能の `manifest.json`、PWA のキャッシュ名に入れます。`v<version>` タグが付いたコミットのビルドはバージョンをそのまま表示し、それ以外のビルドは `0.8.0+1a2b3c4` のようにコミットを付け加えます。これにより、GitHub Pages 上の `main` のページがリリース版と取り違えられることはありません。Chrome の `version` には数字しか入れられないので、そこではコミットは `version_name` に入ります。

```sh
npm version minor           # 0.7.2 -> 0.8.0: package.json、package-lock.json、コミット、タグ v0.8.0
git push --follow-tags      # タグによって .github/workflows/release.yml が開始される
```

リリースワークフローは、タグと `package.json` が一致しなければ停止し、一致すれば `password-manager-<tag>.html`、`password-manager-extension-<tag>.zip`、`SHA256SUMS.txt` を添付します。

## GitHub Pages

`.github/workflows/pages.yml` は、`main` へのプッシュごとにビルドとテストを行い、`build/pages/` を GitHub Pages (Settings → Pages → Source: GitHub Actions) にデプロイします。公開先は <https://password.marketkernel.com/> です。ファイルは単一ファイル版と同じ方法で開きます。最近使ったファイル、設定、記憶されたハンドルはそのアドレスに属し、ディスクから開いたコピーのものとは別になります。

デプロイのたびに `sw.js` 内のキャッシュ名が変わるので、ブラウザは新しいワーカーを自動的に取得します — 接続のある状態で起動したときか、設定 →「更新を確認」が求めたときです。新しいワーカーは自分専用のキャッシュにそのバージョンをダウンロードして待機し、実行中のワーカーはオフラインでも古いページを提供し続けます。設定画面とロック解除画面には「バージョン … の準備ができました。更新」と表示されます。「更新」は、データベースをロックし (他のロックと同様に保存するか確認を求めたうえで)、新しいワーカーを迎え入れてページを再読み込みします。ボタンを使わなくても、アプリのすべてのウィンドウが閉じられれば新しいバージョンが始まります。これはトレードオフでもあります。インストールした PWA は最後のデプロイの内容で動作しますが、ダウンロードしたファイルはそのバージョンのままです。ディスク上でバージョンを固定したい場合は、リリースから `password-manager-<tag>.html` を取得し、`SHA256SUMS.txt` と照合してください。

`npm run test:browser` は `build/pages/` も開きます。サービスワーカーがページを制御下に置くこと、Chrome がマニフェストをインストール可能と判断すること、サーバーを止めてもページが読み込まれ、サンプルデータベースのロックを解除できることを確認します。続けて、新しいデプロイが見つかって待機し、「更新」がそれを迎え入れることも確認します。

## 制限事項

- KDBX 3.1 と 4.x に対応しています。Twofish で暗号化されたファイルと KeePass 1 (`.kdb`) のファイルには対応していません。
- 同期、自動入力 (auto-type)、変更されたコピー同士のマージはありません。
- 拡張機能は Chrome 専用です。フィールドでの候補表示、フォーム送信時のパスワード保存、キーボードショートカットはなく、Web サイトはエントリごとに 1 つです。
- ファイルをその場で書き込めるのは、Chromium ベースのブラウザだけです。
