**Deterministic Password** पासवर्ड फक्त जतन करत नाही, तर ते काढतो. साइटचा पासवर्ड तुमचा
मास्टर पासवर्ड, साइट, तुमचे वापरकर्ता नाव आणि आवृत्ती क्रमांक यांवरून Argon2id आणि
HMAC-SHA-256 द्वारे काढला जातो. डेटाबेस फाइल हरवली, तरी त्याच माहितीवरून कोणत्याही
संगणकावर तेच पासवर्ड पुन्हा मिळतात — त्यामुळे फाइल हरवण्याची भीती उरत नाही. साइटचा पासवर्ड
बदलायचा असेल, तर आवृत्ती वाढवा. हे कसे चालते — "[व्युत्पन्न पासवर्ड](#व्युत्पन्न-पासवर्ड)" पाहा.

शिवाय हा एक पूर्ण KeePass पासवर्ड मॅनेजरही आहे: तो सामान्य `.kdbx` फाइल्स (KDBX 4, AES-256,
Argon2id) उघडतो, संपादित करतो आणि जतन करतो, त्यामुळे तोच डेटाबेस KeePassXC, KeePass किंवा
KeeWeb मध्येही चालत राहतो. व्युत्पन्न पासवर्ड नोंदीत इतर कोणत्याही पासवर्डसारखाच जतन होतो,
आणि इतर KeePass ॲप्सही तो तसाच दाखवतात.

सर्व काही ऑफलाइन चालते: खाते नाही, क्लाउड नाही, नेटवर्क विनंत्या नाहीत. संपूर्ण ॲप एकाच
स्वतंत्र HTML फाइलमध्ये सामावलेले आहे; डेटाबेस पेजच्या मेमरीतच डिक्रिप्ट होतो आणि थेट
डिस्कवर परत जतन होतो, आणि मास्टर पासवर्ड पेजच्या बाहेर कधीच जात नाही. हेच पेज एक
[Chrome एक्स्टेंशन](#chrome-एक्स्टेंशन) देखील आहे, जे शेजारच्या टॅबमध्ये लॉगिन भरते —
**[Chrome Web Store मधून इन्स्टॉल करा](https://chromewebstore.google.com/detail/hiahfdknjchamepclnokcalkcjcfhahf)**.

**[ऑनलाइन आवृत्ती](https://password.marketkernel.com/)** — हेच पेज
PWA (Progressive Web App) म्हणून: ते सिस्टममध्ये इन्स्टॉल करता येते आणि मग स्वतःची विंडो
व स्वतःचा आयकॉन असलेले स्वतंत्र ॲप म्हणून चालते, तसेच ऑफलाइनही काम करते. संगणकावर Chrome,
Edge आणि Arc मध्ये ॲड्रेस बारमधील इन्स्टॉल बटण वापरा; Android वर Chrome चा ⋮ मेनू →
ॲप इन्स्टॉल करा; iOS वर, Safari मध्ये किंवा Chrome मध्ये, शेअर करा → होम स्क्रीनवर जोडा.
तिथेही डेटाबेस तुमच्या डिस्कवरच राहतो — "[GitHub Pages](#github-pages)" पाहा.

## वापर कसा करायचा

1. `build/password-manager.html` बिल्ड करा ("[बिल्ड](#बिल्ड)" पाहा) आणि ती ब्राउझरमध्ये
   उघडा — थेट डिस्कवरून उघडली तरी चालते.
2. "फाइल उघडा" → `.kdbx` डेटाबेस निवडा, किंवा तो विंडोमध्ये ड्रॅग करा.
3. मास्टर पासवर्ड टाका (आणि डेटाबेसला की फाइल असेल तर ती निवडा) → "अनलॉक करा".

Chrome, Edge आणि Arc मध्ये फाइल File System Access API द्वारे उघडली जाते: बदल त्याच
फाइलमध्ये परत लिहिले जातात — आपोआप जतन सुरू असल्यास प्रत्येक बदलानंतर काही क्षणांत — आणि
पुढच्या भेटीत तीच फाइल पुन्हा सुचवली जाते; फक्त तिचे हँडल लक्षात ठेवले जाते, तिचा मजकूर
किंवा पासवर्ड कधीच नाही. Safari आणि Firefox मध्ये फाइल केवळ-वाचन मोडमध्ये उघडते, आणि
"जतन करा" दाबल्यावर डेटाबेसची अद्ययावत प्रत डाउनलोड होते — फोनवरही असेच होते: Android
वरील Chrome मध्ये File System Access नाही, आणि iOS वरील प्रत्येक ब्राउझर, Chrome सुद्धा,
Safari च्याच इंजिनवर चालतो. iOS वर मात्र "जतन करा" प्रत शेअर मेनूकडे देते —
"[फोनवर](#फोनवर)" पाहा.

"नवीन डेटाबेस" AES-256 आणि Argon2id ने (64 MiB, 10 पास — KeePassXC चे डीफॉल्ट, ब्राउझरमध्ये
सुमारे अर्धा सेकंद) एन्क्रिप्ट केलेला रिकामा KDBX 4 डेटाबेस तयार करते.

### फोनवर

900 पिक्सेल रुंदीपर्यंत — फोन, किंवा उभा धरलेला टॅबलेट — पेज एका वेळी एकच गोष्ट दाखवते.
नोंदींची सूची संपूर्ण स्क्रीन व्यापते; नोंदीवर टॅप केल्यास ती स्वतःच्या स्वतंत्र स्क्रीनवर
उघडते, आणि टूलबारमधील ‹, सिस्टमचे "मागे" बटण किंवा मागे स्वाइप केल्यास पुन्हा सूची दिसते.
परत जाताना केलेला बदल जपला जातो, जसा संगणकावर दुसरी नोंद निवडल्यावर जपला जातो; रिकामी
सोडलेली नवीन नोंद टाकून दिली जाते. ☰ गट, टॅग आणि कचरापेटी सूचीवर सरकवून आणतो. मेनू,
जनरेटर आणि सेटिंग्ज स्क्रीनच्या तळातून वर येतात; "मागे" आधी ते बंद करते, आणि डायलॉग रद्द
करते. जनरेटर, सेटिंग्ज आणि लॉक टूलबारच्या ⋯ मेनूमध्ये आहेत.

टच स्क्रीनवर राइट क्लिक आणि ड्रॅग नसतात: गटाशेजारचा ⋯ तोच मेनू उघडतो जो संगणकावर राइट
क्लिकने उघडतो, आणि त्यातील "गटात हलवा…" ड्रॅगचे काम करते. नोंदीचा मेनू म्हणजे नोंदीच्या
स्क्रीनवरील तिचा ⋯.

फाइल केवळ-वाचन मोडमध्ये उघडते. iOS वर "जतन करा" अद्ययावत डेटाबेस शेअर मेनूकडे देते, जिथे
"Save to Files" तो मूळ फाइलच्या जागी ठेवू शकते; मेनू बंद केल्यास बदल जतन न होता राहतात.
Android वरील Chrome फक्त चित्रे, ध्वनी, व्हिडिओ आणि मजकूर शेअर करतो, म्हणून तिथे "जतन करा"
प्रत डाउनलोड करते.

यापेक्षा रुंद स्क्रीनवर, आणि टॅबलेटवर, तिन्ही पॅनेल संगणकावर असतात तशीच राहतात; कोणत्याही
आकाराच्या टच स्क्रीनवर बटणे मोठी होतात आणि गटांशेजारी ⋯ दिसतो.

## Chrome एक्स्टेंशन

**[Chrome Web Store मधून इन्स्टॉल करा](https://chromewebstore.google.com/detail/hiahfdknjchamepclnokcalkcjcfhahf)**

`npm run build` `build/extension/` सुद्धा लिहितो: तेच ॲप Chrome एक्स्टेंशनच्या रूपात, आणि
Chrome Web Store साठी त्याची `build/password-manager-extension-<version>.zip`. स्वतःचा बिल्ड
वापरून पाहण्यासाठी: `chrome://extensions` → डेव्हलपर मोड → अनपॅक केलेले लोड करा → `build/extension`.

टूलबारमधील आयकॉन एक छोटा पॉपअप उघडतो: टॅबमधील साइटच्या नोंदी, ज्यांपैकी एकीवर क्लिक केल्यास
ती भरली जाते, तिचे वापरकर्ता नाव, पासवर्ड किंवा वन-टाइम कोड कॉपी करण्यासाठी बटणे, आणि
संपूर्ण डेटाबेसमध्ये शोध. त्याच्या तळाशी असलेला **पूर्ण मोड** ॲप Chrome च्या साइड पॅनेलमध्ये,
पेजच्या शेजारी, उघडतो — फोन लेआउटमध्ये, कारण पॅनेल अरुंद असते — आणि टॅब बदलले तरी ते
तिथेच राहते. तिथे सर्व काही फाइलमध्ये चालते तसेच चालते; एक्स्टेंशन त्यात भर घालते ती
लॉगिन भरण्याची:

- **पॉपअप** पॅनेलने शेवटी उघडलेली फाइल फक्त मास्टर पासवर्डने अनलॉक करतो: फाइल आणि की फाइल
  निवडणे, आणि प्रत्येक बदल करणे, हे पॅनेलचे काम आहे. ज्या साइटसाठी नोंद नाही तिथे त्याचे
  **नवीन पासवर्ड** बटण पॅनेल जनरेटरवर उघडते, जसे मेनूमधील "भरा" करते.
- पेजच्या संदर्भ मेनूमधील **भरा** (पेजवर किंवा फील्डमध्ये राइट क्लिक) टॅबमधील साइटच्या
  नोंदीचे वापरकर्ता नाव आणि पासवर्ड भरते — किंवा साइन-इनच्या ज्या टप्प्यावर वन-टाइम कोड
  मागितला जातो तिथे तो कोड. साइटसाठी एकच नोंद असेल तर ते लगेच भरते, पॅनेल उघडे असो वा
  नसो; अनेक असतील, एकही नसेल, किंवा डेटाबेस लॉक असेल, तर ते पॅनेल उघडते — नोंद निवडण्यासाठी,
  पासवर्ड तयार करण्यासाठी किंवा अनलॉक करण्यासाठी — आणि मग तिथून पुढे काम चालू ठेवते. दोन
  टप्प्यांचे साइन-इन (Google, Microsoft) पहिल्या टप्प्यावर वापरकर्ता नाव आणि दुसऱ्यावर
  पासवर्ड घेते: टॅबसाठी निवडलेली नोंद लक्षात ठेवली जाते. पॅनेलमधील नोंदीचे **भरा** बटण ती
  नोंद टॅबमध्ये भरते.
- पॅनेल बंद झाल्यावरही **डेटाबेस उघडाच राहतो**, तो लॉक होईपर्यंत: सेटिंग्जमधील निष्क्रियतेच्या
  वेळेनंतर, संगणकाची स्क्रीन लॉक झाल्यावर, पॅनेलमधून, पॉपअपमधून, किंवा टूलबार आयकॉनच्या
  मेनूमधील **लॉक करा** ने. पुन्हा उघडल्यावर पॅनेल पासवर्डशिवाय तोच डेटाबेस पुढे वापरते, आणि
  पॉपअप तो लगेच दाखवतो.
- गट पॅनेलच्या सर्वात वर असलेले **या साइटसाठी** टॅबमधील साइटच्या नोंदी दाखवते, आणि सूची
  त्यावरच उघडते; ते टॅबनुसार बदलत राहते.
- **पेजसाठी नवीन पासवर्ड.** ज्या साइटसाठी नोंद नाही तिथे "भरा" टॅबमधील साइट आणि पेजवर
  टाइप केलेले वापरकर्ता नाव घेऊन "व्युत्पन्न v3" जनरेटर उघडते. त्याचे "भरा" बटण पासवर्ड
  भरते — नोंदणी फॉर्मच्या दोन्ही फील्डमध्ये — आणि तो सामान्य नोंद म्हणून ठेवते.

नोंद टॅबला तेव्हाच जुळते जेव्हा तिची वेबसाइट नेमकी टॅबमधील साइटच दाखवते: दोन्ही पत्ते
जनरेटर 3 च्या `siteOf()` मधून जातात — स्कीम, पोर्ट, पाथ किंवा `www.` नाही, IDN punycode मध्ये.
`google.com` हे `accounts.google.com` ला जुळत नाही, तसेच `mail.site.com` हे `site.com` ला.
`https://` असलेली, किंवा स्कीम नसलेली, नोंद `http://` पेजवर कधीच भरली जात नाही: http वर
वापरल्या जाणाऱ्या साइटच्या नोंदीच्या वेबसाइटमध्ये `http://` हवे. कचरापेटीतील नोंदी सुचवल्या
जात नाहीत, आणि दुसऱ्या साइटसाठी हाताने निवडलेली नोंद दोन्ही साइटची नावे सांगणाऱ्या
इशाऱ्यानंतरच भरली जाते.

**ते कसे बनवले आहे.** पॅनेल म्हणजे पेजच: `panel.html`, आणि Manifest V3 च्या अपेक्षेनुसार
त्याची स्क्रिप्ट `panel.js` मध्ये. प्रत्येक अनलॉक आणि जतनाच्या वेळी ते फाइल आणि तिची की —
`ProtectedValue` मधील पासवर्ड, की फाइल — ऑफस्क्रीन डॉक्युमेंटकडे देते, जे त्या, आणि
त्यांच्या आधारे डिक्रिप्ट केलेली डेटाबेसची केवळ-वाचन प्रत, लॉक होईपर्यंत मेमरीत ठेवते; लॉक
केल्यावर ते बंद होते, आणि की त्याच्यासोबतच जाते. काहीही कुठेही लिहिले जात नाही. मेनू
सर्व्हिस वर्करकडे असतात. "भरा" वर क्लिक झाल्यावर पॅनेल फक्त कोणत्याही प्रतीक्षेच्या (await)
आधीच उघडू शकते, म्हणून वर्करला लगेच कळायला हवे की तो भरू शकतो की नाही: ऑफस्क्रीन डॉक्युमेंट
पाठवते त्याप्रमाणे तो नोंदींच्या वेबसाइट ठेवतो — नावे नाहीत, पासवर्ड नाहीत — आणि ऑफस्क्रीन
डॉक्युमेंट त्याला चालू ठेवते. पॉपअप (`popup.html`, `popup.js`) काहीही डिक्रिप्ट करत नाही: तो
ऑफस्क्रीन डॉक्युमेंटकडून टॅबला जुळणारी शीर्षके आणि वापरकर्ता नावे मागतो, मग क्लिक केलेली ती
एक नोंद; डेटाबेस लॉक असल्यास तो अलीकडील फाइल वाचतो आणि ती उघडण्यासाठी पासवर्डसह त्या
डॉक्युमेंटकडे देतो.

**पेजपर्यंत काय पोहोचते.**

- फक्त क्लिकने जे मागितले तेच, आणि फक्त एका नोंदीची मूल्ये. कोणतीही content script कुठेही
  चालत नाही: क्लिक झाल्यावर `chrome.scripting.executeScript` आधी टॅबच्या प्रत्येक फ्रेमला
  विचारते की ती कुठे आहे आणि तिच्यात कोणती लॉगिन फील्ड आहेत, कोणतीही मूल्ये न पाठवता; मग
  फक्त नोंदीच्या साइटच्या फ्रेमनाच ती मिळतात, आणि टाइप करण्याआधी फंक्शन स्वतःचा पत्ता पुन्हा
  तपासते. त्याच पेजवरील दुसऱ्या साइटच्या फ्रेमला काहीही मिळत नाही.
- फक्त माणसाला दिसणारी फील्डच भरली जातात: दाखवलेली, सक्रिय, लिहिण्यायोग्य, काही आकार
  असलेली, विंडोच्या आत असलेली. सापळा म्हणून लपवलेले फील्ड रिकामेच राहते.
- मूल्ये एक्स्टेंशनच्या isolated world मधून सेट केली जातात, पेजने आपल्या इनपुटवर लावलेल्या
  कोणत्याही setter ला वळसा घालून, आणि `input` व `change` इव्हेंट React, Vue किंवा Angular
  ला याची माहिती देतात.
- मास्टर पासवर्ड, इतर नोंदी आणि साइटची सूची कधीही पेजकडे जात नाहीत.

**परवानग्या.** प्रत्येक साइटऐवजी `activeTab`: आयकॉनवर किंवा "भरा" वर क्लिक केल्यास
एक्स्टेंशनला तो एक टॅब मिळतो. म्हणून पॅनेल पॉपअपमधून किंवा मेनूमधून उघडते, Chrome च्या
स्वतःच्या सेटिंगने (`openPanelOnActionClick`) कधीच नाही: त्या प्रकारे उघडलेल्या पॅनेलला कोणताही टॅब मिळत नाही. जो टॅब दिलेला नाही त्यावर पॅनेलमधील "भरा" नोंदीच्या
साइटसाठी एकदा परवानगी मागते (`optional_host_permissions`). वरील गोष्टींसाठी `contextMenus`,
`scripting` आणि `sidePanel`, डॉक्युमेंटसाठी `offscreen`, स्क्रीन लॉकसाठी `idle`, पॅनेल बंद
असताना कॉपी केलेले गुपित पुसण्यासाठी `clipboardWrite`. `externally_connectable` नाही:
एक्स्टेंशनचे भाग `chrome.runtime` द्वारे एकमेकांशी बोलतात, आणि प्रत्येक भाग फक्त
एक्स्टेंशनच्याच पेजकडून संदेश स्वीकारतो. त्याच्या पेजमध्ये, फाइलप्रमाणेच, `connect-src 'none'`
आहे; बिल्ड हे तपासतो, आणि हेही की कोणत्याही पेजमध्ये inline स्क्रिप्ट किंवा बाहेरचा पत्ता नाही.

फाइलपेक्षा एक फरक: पुन्हा उघडल्यावर पॅनेल डेटाबेस त्याच जागी तेव्हाच लिहिते जेव्हा Chrome
अजूनही तशी परवानगी देत असेल; अन्यथा स्टेटस बार तसे सांगतो, आणि पहिल्यांदा "जतन करा"
दाबल्यावर परवानगी विचारली जाते.

## सुरक्षा

- **पेजमधून काहीही बाहेर जात नाही.** फाइलमधील Content-Security-Policy प्रत्येक नेटवर्क
  विनंती, फॉर्म सबमिशन आणि बाहेरील संसाधनाला मनाई करते; धोरण गहाळ झाल्यास किंवा बाह्य संदर्भ
  आल्यास बिल्ड अयशस्वी होतो. PWA च्या प्रतीत आणखी तीन गोष्टींना परवानगी आहे, सर्व त्याच्याच
  origin वरून: मॅनिफेस्ट, सर्व्हिस वर्कर आणि आयकॉन — `connect-src` `'none'` च राहते.
- फॉरमॅटचा कोड [kdbxweb](https://github.com/keeweb/kdbxweb) आहे — तीच लायब्ररी जिच्यावर KeeWeb
  बनलेले आहे; Argon2 म्हणजे [hash-wasm](https://github.com/Daninet/hash-wasm) चे WebAssembly,
  जे फाइलमध्येच एम्बेड केलेले आहे.
- संरक्षित फील्ड मेमरीत XOR-मास्क करून ठेवली जातात (kdbxweb चे `ProtectedValue`) आणि
  दाखवेपर्यंत स्क्रीनवर लपवलेली असतात. शोध कधीही संरक्षित फील्डमध्ये पाहत नाही.
- **कोणत्याही भाषेतील पासवर्ड.** ब्राउझर एखादे फील्ड पासवर्ड फील्ड समजतो तेव्हा macOS
  Secure Input सुरू करते आणि लॅटिन कीबोर्ड लेआउट सक्तीने लावते, त्यामुळे सिरिलिक मास्टर
  पासवर्ड टाइपच करता येत नाही. Chrome फक्त `type=password` च नव्हे, तर अनुमानाने
  (heuristics) `-webkit-text-security` ने स्टाइल केलेले किंवा ठिपक्यांचे मूल्य असलेले कोणतेही
  फील्ड पासवर्ड समजतो — आणि एकदा तसे समजल्यावर समजतच राहतो. इथली गुप्त फील्ड असा कोणताही
  संकेत देत नाहीत: ती पारदर्शक मजकूर असलेली साधी टेक्स्ट इनपुट आहेत, आणि त्यांच्यावर
  ठिपक्यांचा थर काढला जातो (monospace फॉन्टमध्ये, म्हणजे कर्सर जागेवरच राहतो). एक बॅज
  दाखवतो की लपवलेला मजकूर सिरिलिकमध्ये (РУС) टाइप होत आहे की लॅटिनमध्ये (ENG). याची किंमत:
  Secure Input, जे इतर ॲप्सपासून कीस्ट्रोकही लपवते, कधीच सुरू होत नाही.
- कॉपी केलेले गुपित 30 सेकंदांनंतर आणि लॉक झाल्यावर क्लिपबोर्डवरून पुसले जाते.
- 15 मिनिटे निष्क्रिय राहिल्यावर, आणि `⌘L` दाबल्यावर, डेटाबेस लॉक होतो. लॉक केल्यावर
  डिक्रिप्ट केलेला डेटाबेस मेमरीतून काढला जातो; जतन न केलेले बदल लिहिता येत नसतील तर लॉक
  ते बदल फेकून देण्याऐवजी थांबून राहते.
- नोंदींमधील लिंक फक्त `http`, `https`, `ftp` आणि `mailto` साठी, `noopener` सह उघडतात.
- पासवर्ड `crypto.getRandomValues` आणि rejection sampling ने तयार होतात: प्रत्येक अक्षर येण्याची
  शक्यता सारखीच असते.

## व्युत्पन्न पासवर्ड

जनरेटरमधील **व्युत्पन्न v3** पुढील गोष्टींवरून पासवर्ड काढतो:

- डेटाबेसचा मास्टर पासवर्ड (की फाइल असल्यास ती विचारात घेतली जात नाही), किंवा तिथे टाइप
  केलेला दुसरा मास्टर पासवर्ड,
- वापरकर्ता नाव,
- साइट — खाते ज्या डोमेनवर आहे ते (`https://www.github.com/login` → `github.com`),
- आवृत्ती — 1, 2, … 2³² − 1 पर्यंत; "+1" त्याच खात्याला नवीन पासवर्ड देते.

या चारांपासून 32 बाइट एन्ट्रॉपी तयार होते. आवश्यकता — लांबी, अक्षर संच, सारखी दिसणारी
अक्षरे — फक्त त्या बाइटना अक्षरांचे रूप देतात: त्या बदलल्याने एन्ट्रॉपी बदलत नाही. **वापरा**
परिणाम नोंदीत सामान्य, जतन केलेला पासवर्ड म्हणून ठेवते. तो कसा बनवला याची कोणतीही माहिती
ठेवली जात नाही: ती नोंद इतर कोणत्याही नोंदीसारखीच असते, आणि इतर KeePass ॲप्सही तोच पासवर्ड
दाखवतात. फाइल हरवली, तरी तोच मास्टर पासवर्ड, वापरकर्ता नाव, साइट, आवृत्ती आणि आवश्यकता
कोणत्याही मशीनवर तोच पासवर्ड देतात. डीफॉल्ट: 20 अक्षरे, चारही अक्षर संच, सारखी दिसणारी
अक्षरे नाहीत; इतर आवश्यकतांनी बनवलेल्या पासवर्डसाठी त्याही लक्षात ठेवाव्या लागतात.

जनरेटर आधी वापरकर्ता नाव विचारतो — नोंदीतून उघडल्यास नोंदीचेच: तिथे जे टाइप केले ते फॉर्ममध्येही
दिसते — मग साइट; दोन्ही आवश्यक आहेत, आणि त्यांच्यापासून मिळणारा पासवर्ड तळाशी, **वापरा** च्या
वर असतो.

- ईमेल पत्ता असलेले वापरकर्ता नाव स्वतःच साइट सांगते: `test@site.com` मुळे `site.com` भरले
  जाते, आणि नोंदीची वेबसाइट जशी आहे तशीच राहते — ती `mail.site.com` असू शकते. पण एकाच
  पत्त्याने अनेक साइटवर साइन इन केले जाते, आणि जनरेटर फील्डखाली तसे सांगतो: `test@gmail.com`
  ने GitHub साठी पासवर्ड हवा असेल, तर त्याने भरलेल्या `gmail.com` च्या जागी `github.com` टाइप करा.
- इतर कोणत्याही वापरकर्ता नावासाठी साइट टाइप करावी लागते, आणि नोंदीतून उघडल्यास जे टाइप केले
  तीच तिची वेबसाइटही होते. सुरुवातीला नोंदीची सध्याची वेबसाइट भरलेली असते.

साइट म्हणून टाइप केलेल्या मजकुरातील स्कीम, पाथ, पोर्ट आणि सुरुवातीचे `www.` यांना महत्त्व
नाही; सबडोमेनला आहे — `login.github.com` आणि `github.com` या दोन वेगळ्या साइट आहेत. URL
नसलेली साइट ("माझी बँक") जशी आहे तशी वापरली जाते. टूलबारमधून उघडल्यास जनरेटर याच प्रकारे,
स्वतःच्या फील्डसह, काम करतो आणि परिणाम कॉपी करतो.

जनरेटर उघडताना प्रत्येक वेळी "डेटाबेसचा मास्टर पासवर्ड वापरा" वर खूण असते. दुसऱ्या मास्टर
पासवर्डवरून काढण्यासाठी खूण काढा — तो तिथेच टाइप केला जातो आणि कुठेही ठेवला जात नाही —
दुसऱ्या डेटाबेसमध्ये, किंवा मास्टर पासवर्ड बदलण्याआधी, बनवलेला पासवर्ड परत मिळवण्यासाठी.
मास्टर पासवर्ड बदलल्याने फाइलमधील पासवर्ड जसे आहेत तसेच राहतात; फक्त त्यानंतर जनरेटर जे
काढतो ते वेगळे असते.

### अल्गोरिदम: जनरेटर 3

खालील सर्व काही गोठवलेले आहे: कोणताही स्थिरांक बदलल्यास त्याने बनवलेला प्रत्येक पासवर्ड पुन्हा
काढणे अशक्य होईल. भविष्यातील जनरेटर सूचीत नवीन प्रकार म्हणून येईल आणि हा जसा आहे तसा राहील.
कोड `src/core/derived.ts` मध्ये आहे; `npm test` तो निश्चित व्हेक्टरविरुद्ध, आणि या वर्णनावरून
Node च्या स्वतःच्या `crypto` ने लिहिलेल्या स्वतंत्र अंमलबजावणीविरुद्ध तपासतो. मूलघटक प्रमाणित
आहेत — SHA-256, HMAC-SHA-256, Argon2id — त्यामुळे अल्गोरिदम कोणत्याही भाषेत पुन्हा लिहिता येतो.

तो दोन टप्प्यांत चालतो: गुपितांपासून 32 बाइट एन्ट्रॉपी बनते, मग आवश्यकता त्या बाइटमधून
अक्षरे घडवतात.

**टप्पा 1 — एन्ट्रॉपी.**

1. *इनपुटचे सामान्यीकरण.* सर्व स्ट्रिंग UTF-8 मध्ये.
   - `site` — साइट म्हणून टाइप केलेल्या मजकुराचा होस्ट: मजकूर WHATWG URL म्हणून पार्स केला
     जातो (मजकुरात `scheme://` नसल्यास सुरुवातीला `https://` जोडले जाते): लहान अक्षरे, IDN
     punycode मध्ये, पोर्ट नाही, वापरकर्ता नाव किंवा पासवर्ड नाही, सुरुवातीचे `www.` काढले जाते;
     URL म्हणून पार्स न होणारा मजकूर जसा आहे तसा वापरला जातो. मग ट्रिम, NFC-सामान्यीकरण,
     लहान अक्षरांत रूपांतर.
   - `user` — वापरकर्ता नाव, ट्रिम आणि NFC-सामान्यीकृत; लहान-मोठी अक्षरे जशी आहेत तशी राहतात.
   - `master` — मास्टर पासवर्ड, NFC-सामान्यीकृत, काहीही ट्रिम केले जात नाही. एक अक्षर म्हणून
     टाइप केलेला "é" आणि "e" अधिक जोडचिन्ह (combining accent) म्हणून टाइप केलेला "é" एकच
     पासवर्ड देतात.
2. *सॉल्ट.*
   ```
   salt = SHA-256( "html-password-manager/derived/v3" ‖ 0x00
                   ‖ u32be(byte length of site) ‖ site
                   ‖ u32be(byte length of user) ‖ user
                   ‖ u32be(version) )
   ```
   लांबीचे उपसर्ग `ab` + `c` आणि `a` + `bc` यांना वेगळे ठेवतात; लेबल हे बाइट त्याच इनपुटच्या
   इतर कोणत्याही वापरापासून वेगळे ठेवते. `u32be` म्हणजे 4 बाइटचा big-endian पूर्णांक.
3. *स्ट्रेचिंग.*
   ```
   entropy = Argon2id(password = master, salt, memory = 64 MiB, passes = 3,
                      lanes = 1, version 0x13, output = 32 bytes)
   ```
   Argon2id मास्टर पासवर्डच्या प्रत्येक अंदाजासाठी 64 MiB मेमरी खर्च करायला लावतो, आणि
   त्यामुळेच GPU आणि ASIC मंदावतात. साइट, वापरकर्ता नाव आणि आवृत्ती सॉल्टमध्ये असल्यामुळे
   प्रत्येक खात्याचे स्वतःचे सॉल्ट असते: कोणतेही टेबल आधीच काढून ठेवता येत नाही, आणि प्रत्येक
   खात्यावर स्वतंत्रपणे हल्ला करावा लागतो.

**टप्पा 2 — आकार देणे.** आवश्यकता फक्त इथेच वापरल्या जातात, त्यामुळे त्या पासवर्ड कसा दिसतो
ते बदलतात, त्यामागची एन्ट्रॉपी नाही.

4. *यादृच्छिक बाइटचा प्रवाह*, हवा तितका लांब — लांब पासवर्ड आणि त्याच्या फेरमांडणीसाठी 32 बाइट
   पुरेसे नाहीत:
   ```
   block(i) = HMAC-SHA-256(key = entropy, "hpm-v3-stream" ‖ u32be(i)),  i = 0, 1, 2, …
   ```
5. *n पेक्षा लहान, पक्षपातरहित संख्या.* प्रवाहातील पुढचे 4 बाइट big-endian u32 `x` म्हणून
   घ्या. जर `x ≥ 2³² − (2³² mod n)`, तर तो टाकून द्या आणि पुढचा घ्या; अन्यथा परिणाम `x mod n`
   असतो. (नुसते `x mod n` घेतल्यास वर्णमालेच्या सुरुवातीच्या अक्षरांना झुकते माप मिळाले असते.)
6. *अक्षरे.* संच, याच क्रमाने, प्रत्येक फक्त निवडला असल्यास:
   ```
   A–Z      ABCDEFGHIJKLMNOPQRSTUVWXYZ
   a–z      abcdefghijklmnopqrstuvwxyz
   0–9      0123456789
   symbols  !#$%&*+-=?@^_~.,:;()[]{}<>/|
   ```
   सारखी दिसणारी अक्षरे नको असतील, तर त्यांच्यातून `O 0 o I l 1 |` काढले जातात. मग:
   ```
   chars = []
   for each chosen set:            chars.push(set[draw(|set|)])      # every set is present
   while |chars| < length:         chars.push(all[draw(|all|)])      # all = the sets joined
   for i = length − 1 down to 1:   j = draw(i + 1); swap chars[i], chars[j]   # Fisher–Yates
   password = chars joined
   ```
   लांबी 4 ते 128. आधी प्रत्येक संचातून एक अक्षर घेतल्यामुळेच "अंक आहे" आणि "चिन्ह आहे" याची
   हमी मिळते; फेरमांडणी ती अक्षरे कुठे गेली ते लपवते.

**टेस्ट व्हेक्टर.** मास्टर पासवर्ड `Тестовый пароль`, साइट `https://www.github.com/login`
(`github.com`), वापरकर्ता नाव `me@example.com`, आवृत्ती 1, डीफॉल्ट आवश्यकता
(20 अक्षरे, चारही संच, सारखी दिसणारी अक्षरे नाहीत):

```
password  A6qVXXF]7<%a)aa<x7*U
```

तीच एन्ट्रॉपी 12 अक्षरे आणि चिन्हांशिवाय `yaM6VJaJFYUQ` देते; डीफॉल्ट आवश्यकतांसह आवृत्ती 2
`3q_bwppbE8P2+ufKr:P6` देते.

### तो किती मजबूत आहे

- व्युत्पन्न पासवर्डमध्ये जास्तीत जास्त 256 बिट एन्ट्रॉपी असते (32 बाइट); सारखी दिसणारी अक्षरे
  वगळून चारही संचांतील 20 अक्षरे म्हणजे सुमारे 128 बिट. व्यवहारात मर्यादा मास्टर पासवर्डचीच
  असते.
- **कोणत्याही व्युत्पन्न-पासवर्ड पद्धतीचा कमकुवत दुवा:** एखाद्या साइटवरून लीक झालेल्या
  पासवर्डच्या आधारे हल्लेखोर ऑफलाइन मास्टर पासवर्डचा अंदाज लावू शकतो, कारण साइट आणि
  वापरकर्ता नाव माहीत असतात. प्रत्येक अंदाजासाठी 64 MiB वर एक Argon2id रन लागतो — ब्राउझरमध्ये
  सुमारे 0.15–0.4 s, खास हार्डवेअरवर त्याहून कमी. लहान किंवा सामान्य मास्टर पासवर्ड सापडेल;
  लांब पासफ्रेज सापडणार नाही. यादृच्छिक पासवर्डमध्ये ही कमजोरी नसते, म्हणूनच जनरेटरमध्ये
  दोन्ही आहेत.
- मास्टर पासवर्ड टिकून आहे तोपर्यंत, लीक झालेला पासवर्ड इतर साइट किंवा आवृत्त्यांबद्दल काहीही
  उघड करत नाही: ते इतर सॉल्टमधून, म्हणजे इतर Argon2 रनमधून येतात.

डेटाबेस उघडा असताना मास्टर पासवर्ड, आतापर्यंत काढलेल्या एन्ट्रॉपीसह, मेमरीत XOR-मास्क करून
ठेवला जातो; लॉक केल्यावर दोन्ही काढून टाकले जातात.

## जुने अल्गोरिदम

दोन जुने Windows प्रोग्राम गुप्त वाक्यांशांवरून पासवर्ड काढत असत; जनरेटरमधील **व्युत्पन्न v1** (लेगसी 1)
आणि **व्युत्पन्न v2** (लेगसी 2) त्यांची हुबेहूब पुनरावृत्ती करतात, त्यामुळे त्यांनी बनवलेले पासवर्ड
परत मिळवता येतात. ते कॅल्क्युलेटर आहेत: त्यांत टाइप केलेले काहीही जतन होत नाही, जनरेटर बंद
झाल्यावर वाक्यांश नाहीसे होतात, आणि **वापरा** परिणाम नोंदीत सामान्य, जतन केलेला पासवर्ड
म्हणून ठेवते. सेटिंग्ज → "जुने पासवर्ड अल्गोरिदम दाखवा" सुरू केल्यावर ते दिसू लागतात.

नोंदीतून उघडल्यास दोन्ही ओळखकर्ता सुचवतात: आधीच साइट सांगणारे वापरकर्ता नाव
(`mail@site.com`) जसे आहे तसे, नाहीतर वापरकर्ता नाव, `@` आणि `www.` शिवाय साइट
(`dmytro@github.com`); तो बदलता येतो. प्रत्येक वाक्यांशासाठी — मास्टर की आणि दुय्यम की,
प्राथमिक आणि दुय्यम गुप्त वाक्यांश — स्वतःचा "डेटाबेस लॉक होईपर्यंत लक्षात ठेवा"
बॉक्स आहे: खूण केलेला वाक्यांश पेजच्या मेमरीत, XOR-मास्क करून, ठेवला जातो आणि पुढच्या वेळी
भरला जातो; पहिला वाक्यांश ठेवलेला असल्यास की लगेच काढली जाते. दोन्ही अल्गोरिदम डेटाबेसचा
स्वतःचा मास्टर पासवर्ड — ज्याने तो अनलॉक केला तो — पहिला वाक्यांश म्हणूनही घेऊ शकतात: लेगसी 1
ची मास्टर की किंवा लेगसी 2 चा प्राथमिक गुप्त वाक्यांश ("डेटाबेसचा मास्टर पासवर्ड वापरा",
प्रत्येकासाठी सेटिंग्जमध्ये लक्षात ठेवले जाते): तेव्हा ते फील्ड आणि त्याचा बॉक्स बंद होतात. यातील
काहीही डिस्कवर लिहिले जात नाही; लॉक केल्यावर,
डेटाबेस बंद केल्यावर किंवा जुने अल्गोरिदम बंद केल्यावर हे सर्व विसरले जाते. कोड
`src/core/legacy.ts` मध्ये आहे; `npm test` तो मूळ .NET प्रोग्रामनी काढलेल्या व्हेक्टरविरुद्ध तपासतो.

**लेगसी 1** — मास्टर की, ओळखकर्ता, प्राथमिक की, दुय्यम की, परिणाम:

```
short(bytes) = Base64(bytes) without "=", "/", "+", first 10 characters
primary key  = short(SHA-1 applied 1 000 000 times to UTF-8(master key ‖ identifier))
result       = short(SHA-1(UTF-8(primary key ‖ secondary key)))
```

प्राथमिक की ओळखकर्त्याशी जोडलेली असते आणि वेगळी (कागदावर) ठेवता येते, त्यामुळे मास्टर की
कुठेही टाइप करावी लागत नाही: प्राथमिक की थेट टाकता येते. दुय्यम कीमुळे चोरलेली चिठ्ठी एकटी
निरुपयोगी ठरते.

**लेगसी 2** (Password.Generator 1.0) — प्राथमिक संरक्षण: ओळखकर्ता, प्राथमिक गुप्त वाक्यांश,
कीची लांबी, अक्षर संच; दुय्यम संरक्षण: की, दुय्यम गुप्त वाक्यांश, पासवर्डची आवृत्ती, पासवर्डची
लांबी, अक्षर संच:

```
digest(a, b, v, n) = SHA-1 applied n times to UTF-8(a) ‖ UTF-8(b) ‖ (v > 0 ? u32le(v) : nothing)
key                = select(digest(identifier, primary phrase, 1, 100 000), key length + 2)
password           = select(digest(key, secondary phrase, version, 1), password length + 2)
```

`select` डायजेस्ट पाच little-endian u32 म्हणून वाचते, प्रत्येकाचा सर्वोच्च बिट सेट करते, आणि
तो वर्णमालेच्या N आधारात लिहिते — `!#$%&'()+,-.` (निवडल्यास), अंक (नेहमी), A–Z, a–z
(निवडल्यास) — सर्वात कमी महत्त्वाचा अंक आधी; प्रत्येकातील 5 अक्षरे ठेवते आणि लांबीपर्यंत
(1–18) कापते. पहिली दोन अक्षरे स्वाक्षरी असतात — प्रोग्रामने दाखवलेल्या स्वाक्षरीशी डोळ्यांनी
जुळवून पाहण्यासाठी; उरलेली अक्षरे म्हणजे की किंवा पासवर्ड. कीची आवृत्ती नेहमी 1 असते:
प्रोग्राममध्ये तिच्यासाठी फील्डच नाही. ओळखकर्ता `1`, वाक्यांश `1`, लांबी 10, अंक आणि अक्षरे
यांवरून की `E8 8pgYm9fZha` मिळते.

दोन्ही आवृत्ती 3 पेक्षा खूपच कमकुवत आहेत: वाक्यांशांचा एक अंदाज हल्लेखोराला 64 MiB वरील
Argon2id रनऐवजी फक्त काही SHA-1 रनइतकाच महाग पडतो, आणि लेगसी 1 चा परिणाम 10 अक्षरांचा,
सुमारे 60 बिट असतो. ते जुने पासवर्ड परत मिळवण्यासाठी वापरा, नवीन पासवर्डसाठी नाही.

## भाषांतरे

इंग्रजी मजकूर कोडमध्येच राहतो: `t('menu', 'Delete')`, `tn('status', '{count} entry',
'{count} entries', n)`, आणि टेम्पलेटमध्ये `data-i18n="context"` / `data-i18n-attr="context"`.
पहिला आर्ग्युमेंट म्हणजे संदर्भ (context) — इंटरफेसचा तो भाग ज्यात स्ट्रिंग येते, त्यामुळे तोच
इंग्रजी शब्द दोन ठिकाणी वेगवेगळ्या प्रकारे भाषांतरित करता येतो. शब्दकोश,
`src/locales/<code>.json`, संदर्भ → इंग्रजी मजकूर → भाषांतर अशी जोडणी करतो:

```json
{
  "menu": { "Delete": "Удалить" },
  "status": { "{count} entries": { "one": "{count} запись", "few": "{count} записи", "many": "{count} записей", "other": "{count} записи" } }
}
```

शब्दकोशात नसलेली स्ट्रिंग इंग्रजीत दाखवली जाते. संख्या असलेल्या मजकुराचे भाषेच्या प्रत्येक
अनेकवचन वर्गासाठी (`Intl.PluralRules`) एक रूप असते, इंग्रजी अनेकवचनी रूपाच्या कीखाली.
`npm run i18n` प्रत्येक भाषेसाठी अद्याप भाषांतर न झालेल्या आणि आता न वापरल्या जाणाऱ्या स्ट्रिंगची
यादी देतो; `npm test` तपासतो की प्रत्येक भाषांतरात इंग्रजी प्लेसहोल्डर कायम आहेत आणि सर्व
अनेकवचनी रूपे आहेत.

Chrome एक्स्टेंशनबद्दल स्वतः जे दाखवतो — त्याचे नाव आणि वर्णन, टूलबार बटणाचे शीर्षक — ते
पॅनेलच्या नव्हे तर ब्राउझरच्या भाषेनुसार, `chrome.i18n` द्वारे, दिसते. हे मजकूर
`src/extension/manifest.json` मधील इंग्रजी मजकूर आहेत, आणि त्याच शब्दकोशांत `manifest` या
संदर्भाखाली भाषांतरित केलेले आहेत; बिल्ड ते `_locales/<code>/messages.json` मध्ये लिहितो आणि
मॅनिफेस्टमध्ये `__MSG_appName__` आणि तत्सम नोंदी ठेवतो. Chrome चे स्वतःचे कोड आहेत आणि तो
बाकीचे कोड दुर्लक्षित करतो: `pt` चे `pt_BR` आणि `pt_PT` होतात, `zh` चे `zh_CN`, आणि उर्दूसाठी
कोडच नाही, म्हणून तिथे Chrome एक्स्टेंशनचे नाव इंग्रजीत दाखवतो. 75 अक्षरांपेक्षा लांब नाव
किंवा 132 पेक्षा लांब वर्णन असल्यास बिल्ड थांबतो.

हे README देखील भाषांतरित आहे: `docs/readme/README.<code>.md`, प्रत्येक भाषेसाठी एक, आणि
प्रत्येकाच्या सुरुवातीला भाषांची सूची. इथे केलेला बदल भाषांतरांमध्येही व्हायला हवा.

## बिल्ड

```sh
./build.sh         # installs the dependencies if needed, then builds build/password-manager.html
npm install
npm run build      # -> build/password-manager.html
npm run watch      # rebuild on changes in src/
npm run typecheck  # tsc --noEmit
npm test           # opening, editing and saving .kdbx files, the generator, TOTP, derived passwords, matching tabs, the dictionaries
npm run test:browser  # the built page and the extension in headless Chrome
npm run i18n       # strings each dictionary lacks or no longer needs
npm run check      # typecheck, test, build and test:browser in a row
npm run shots -- shots/after  # build, then screenshots of the main screens into shots/after
```

`build.mjs` esbuild च्या मदतीने `src/app/main.ts` एका IIFE मध्ये बंडल करतो आणि ते, स्टाइल आणि
आयकॉनसह (data URI), `src/app/template.html` मध्ये बसवतो. Node साठी असलेले kdbxweb चे पर्याय
(`crypto`, `@xmldom/xmldom`) रिकाम्या स्टबने बदलले जातात — ब्राउझरमध्ये `crypto.subtle`
आणि `DOMParser` असतातच. परिणाम म्हणजे `build/password-manager.html`, सुमारे 500 KB, ज्यापैकी एक चतुर्थांश शब्दकोश आहेत.

त्याच रनमध्ये `build/pages/` लिहिले जाते: तेच पेज इन्स्टॉल करता येणाऱ्या PWA च्या रूपात —
मॅनिफेस्ट लिंक आणि सर्व्हिस वर्करच्या नोंदणीसह `index.html`, `manifest.webmanifest`, आयकॉन आणि
`sw.js`, जो पेज कॅश करतो जेणेकरून ते ऑफलाइनही उघडते. `build/password-manager.html` स्वतः
कोणत्याही बाह्य संदर्भांशिवाय एकच फाइल राहते.

आणि `build/extension/`: `panel.html` म्हणजे `panel.js` मधील स्क्रिप्टसह टेम्पलेट — तोच
`src/app/main.ts`, पण `src/app/platform.ts` च्या जागी `src/extension/extension.ts` (फाइलमध्ये `platform.ts` चे हुक काहीही करत नाहीत)
— आणि त्याच्या शेजारी `popup.html` (पेजच्या स्टाइल आणि `popup.css` सह) आणि `popup.js`,
`background.js`, `offscreen.html` आणि `offscreen.js`, आयकॉन आणि
`manifest.json`, ज्याची आवृत्ती `package.json` मधून घेतली जाते. `build/password-manager-extension-<version>.zip`
मध्ये याच फाइल, निश्चित तारखांसह, असतात: तेच स्रोत नेहमी तेच बाइट देतात.

`tests/extension.mjs` ते एक्स्टेंशन DevTools प्रोटोकॉलद्वारे headless Chrome मध्ये लोड करतो
(pipe वरून `Extensions.loadUnpacked`; आवृत्ती 137 पासून Chrome मध्ये `--load-extension` राहिलेले
नाही) आणि लोकल सर्व्हरवरील टेस्ट साइटवर भरतो: साधा फॉर्म, React सारखा फॉर्म, वन-टाइम कोडसह
तीन टप्प्यांचे साइन-इन, साइटच्या स्वतःच्या आणि दुसऱ्या साइटच्या फ्रेम, सापळा म्हणून लपवलेली
फील्ड, https नोंदीसाठी http पेज, व्युत्पन्न
v3 पासवर्डने भरलेली नोंदणी — पॅनेल बंद असताना, आणि लॉकनंतर; आणि पॉपअप, जो अनलॉक करतो, भरतो,
शोधतो, कॉपी करतो आणि लॉक करतो. संदर्भ मेनूवर
DevTools मधून क्लिक करता येत नाही, म्हणून टेस्ट वर्करचे `onClicked` स्वतःच चालवते; खरा क्लिक नसल्याने Chrome
`activeTab` देत नाही, म्हणून चाचणीखालील प्रत host permissions म्हणून टेस्ट साइटपर्यंत, `*.test`, पोहोचू शकते.
टूलबार आयकॉनवर DevTools मधून क्लिक करता येतो (`Extensions.triggerAction`): स्वतंत्र Chrome,
बिल्ड झालेल्या एक्स्टेंशनसह, तपासतो की त्या क्लिकने पॉपअपला टॅब मिळतो. Headless Chrome 153
त्या क्लिकवर क्रॅश होतो, एक्स्टेंशन कोणतेही असो, आणि मग ही तपासणी वगळली जाते; Chrome for Testing
ती चालवतो (`CHROME=/path/to/chrome-for-testing npm run test:browser`).

`tests/fixtures/Database.kdbx` हा टेस्टसाठीचा नमुना डेटाबेस आहे; त्याचा पासवर्ड `Тестовый пароль` आहे.

## आवृत्त्या आणि रिलीज

आवृत्ती एकाच ठिकाणी लिहिली जाते: `package.json`. बिल्ड ती पेजमध्ये (उघडण्याच्या स्क्रीनखालील
ओळ, सेटिंग्जचा तळ), एक्स्टेंशनच्या `manifest.json` मध्ये आणि PWA च्या कॅशच्या नावात टाकतो.
`v<version>` टॅग असलेल्या कमिटचा बिल्ड ती जशी आहे तशी दाखवतो; इतर कोणताही बिल्ड तिच्यापुढे
आपला कमिट जोडतो, `0.8.0+1a2b3c4`, जेणेकरून GitHub Pages वरील `main` चे पेज रिलीज समजले जाऊ नये.
Chrome च्या `version` मध्ये फक्त संख्या असतात, म्हणून तिथे कमिट
`version_name` मध्ये जातो.

```sh
npm version minor           # 0.7.2 -> 0.8.0: package.json, package-lock.json, a commit and the tag v0.8.0
git push --follow-tags      # the tag starts .github/workflows/release.yml
```

टॅग आणि `package.json` जुळत नसल्यास रिलीज workflow थांबतो; नाहीतर तो
`password-manager-<tag>.html`, `password-manager-extension-<tag>.zip` आणि `SHA256SUMS.txt` जोडतो.

## GitHub Pages

`.github/workflows/pages.yml` `main` वरील प्रत्येक push बिल्ड आणि टेस्ट करतो आणि
`build/pages/` GitHub Pages वर डिप्लॉय करतो (Settings → Pages → Source: GitHub Actions),
<https://password.marketkernel.com/> या पत्त्यावर. फाइल एकल फाइलप्रमाणेच
उघडतात; अलीकडील फाइल, सेटिंग्ज आणि लक्षात ठेवलेले हँडल त्या पत्त्याचे असतात;
डिस्कवरून उघडलेल्या प्रतीचे ते वेगळे असतात.

प्रत्येक डिप्लॉय `sw.js` मधील कॅशचे नाव बदलतो, त्यामुळे ब्राउझर नवीन आवृत्ती आपोआप घेतो;
उघडी विंडो पुढच्या रीलोडला तिच्यावर जाते. हीच तडजोडही आहे: इन्स्टॉल केलेले PWA शेवटच्या
डिप्लॉयने तिथे जे ठेवले ते चालवते, तर डाउनलोड केलेली फाइल ज्या आवृत्तीची आहे त्याच आवृत्तीची
राहते. डिस्कवर निश्चित आवृत्ती हवी असल्यास रिलीजमधून `password-manager-<tag>.html` घ्या आणि
`SHA256SUMS.txt` शी पडताळून पाहा.

`npm run test:browser` `build/pages/` सुद्धा उघडतो: सर्व्हिस वर्कर पेजचा ताबा घेतो, Chrome
मॅनिफेस्ट इन्स्टॉल करण्यायोग्य मानतो, आणि सर्व्हर बंद झाल्यावरही पेज लोड होते आणि नमुना डेटाबेस
अनलॉक करते.

## मर्यादा

- KDBX 3.1 आणि 4.x समर्थित आहेत; Twofish ने एन्क्रिप्ट केलेल्या फाइल आणि KeePass 1 (`.kdb`)
  फाइल समर्थित नाहीत.
- सिंक, ऑटो-टाइप किंवा बदललेल्या प्रतींचे विलीनीकरण नाही.
- एक्स्टेंशन फक्त Chrome साठी आहे, आणि त्यात फील्डमध्ये सूचना नाहीत, फॉर्म पाठवताना पासवर्ड
  जतन करणे नाही, कीबोर्ड शॉर्टकट नाही, आणि प्रत्येक नोंदीसाठी एकच वेबसाइट.
- फक्त Chromium-आधारित ब्राउझर फाइल तिच्याच जागी लिहू शकतात.
